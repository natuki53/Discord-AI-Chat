# 要件仕様書

## 1. 要件の読み方

- `MUST`: MVP 完了に必須。
- `SHOULD`: 原則実装するが、実機制約で次リリースへ送る余地がある。
- `MAY`: 将来拡張。
- すべての Discord ID は JavaScript の `number` ではなく文字列で扱う。

## 2. アクター

| アクター         | 説明                                                            |
| ---------------- | --------------------------------------------------------------- |
| Guild管理者      | Botを導入し、対象チャンネル・応答モード・Botペルソナを設定する  |
| チャンネル利用者 | 対象チャンネルで会話し、AIの応答を受ける                        |
| Bot運用者        | SSH、設定ファイル、Docker Compose、ログ、バックアップを管理する |
| ローカルLLM      | 会話生成、話題要約、ツール選択を行う                            |
| 検索サービス     | 最新情報の検索結果を返す                                        |
| Webサイト        | 検索結果の根拠本文を返す非信頼データ源                          |

## 3. 機能要件

### 3.1 Discord接続と対象範囲

| ID         | 優先   | 要件                                                               | 受入条件                                                |
| ---------- | ------ | ------------------------------------------------------------------ | ------------------------------------------------------- |
| FR-DIS-001 | MUST   | Botは設定されたGuild IDだけを処理する                              | 未登録Guildのイベントが保存も応答もされない             |
| FR-DIS-002 | MUST   | Botはallowlistのチャンネルだけを処理する                           | 未登録チャンネルのイベントが保存も応答もされない        |
| FR-DIS-003 | MUST   | `Guilds`、`GuildMessages`、`MessageContent` のintentを使用する     | 通常メッセージ本文を受信できる                          |
| FR-DIS-004 | MUST   | 人間による新規メッセージを受信する                                 | 対象メッセージが永続化され処理ジョブが作られる          |
| FR-DIS-005 | MUST   | 自分、他Bot、Webhook、システムメッセージを応答トリガーから除外する | Bot同士のループが起きない                               |
| FR-DIS-006 | MUST   | メッセージ編集を反映する                                           | 未処理なら最新内容を使用し、処理後なら要約をdirtyにする |
| FR-DIS-007 | MUST   | メッセージ削除を反映する                                           | 本文を削除し、以後の文脈へ含めない                      |
| FR-DIS-008 | MUST   | Discordイベントを冪等処理する                                      | 同じmessage IDを複数回受信しても応答は1回以下           |
| FR-DIS-009 | SHOULD | Threadを親チャンネルとは別の会話単位として扱う                     | Thread内の話題が親チャンネルへ混ざらない                |
| FR-DIS-010 | MUST   | DMを処理しない                                                     | DMイベントを保存・応答しない                            |

### 3.2 会話ターンと応答制御

| ID         | 優先   | 要件                                                    | 受入条件                                       |
| ---------- | ------ | ------------------------------------------------------- | ---------------------------------------------- |
| FR-CON-001 | MUST   | 対象チャンネルの全対象メッセージをキューへ入れる        | 高頻度投稿テストで欠落しない                   |
| FR-CON-002 | MUST   | チャンネルごとに処理順を直列化する                      | 同一チャンネルのAI応答順が入力順と矛盾しない   |
| FR-CON-003 | MUST   | 短時間の連投を会話ターンへ束ねる                        | debounce窓内の投稿にAIが何重にも割り込まない   |
| FR-CON-004 | MUST   | 返信先、mention、話者、時刻、message IDを文脈へ含める   | 誰への返答かを会話テストで識別できる           |
| FR-CON-005 | MUST   | 応答中はtypingを定期更新する                            | 生成待ち中に利用者が停止と誤解しない           |
| FR-CON-006 | MUST   | 生成中に新発言が加わった場合にstale判定する             | 古い生成が新話題へ割り込まない                 |
| FR-CON-007 | MUST   | `all`、`ambient`、`mention`、`paused` の4モードを持つ   | 設定変更後、各モードの挙動になる               |
| FR-CON-008 | MUST   | `all` では各会話ターンへ原則1回返答する                 | 単発発言は1回、debounce内連投はまとめて1回返答 |
| FR-CON-009 | MUST   | `ambient` では参加判定が`respond`のときだけ返答する     | `silent`判定ではDiscordへ投稿しない            |
| FR-CON-010 | MUST   | `mention` ではBot mentionまたはBotへのreplyだけ返答する | 通常会話へ割り込まない                         |
| FR-CON-011 | MUST   | Discord投稿上限に合わせて安全に分割する                 | 長文でも文字欠落とmention暴発がない            |
| FR-CON-012 | MUST   | `allowedMentions`を無効化する                           | AI生成の`@everyone`等で通知が飛ばない          |
| FR-CON-013 | SHOULD | cooldownと最大キュー長を設定できる                      | 会話の洪水時に負荷と投稿を制御できる           |

推奨既定値:

- debounce: 2.5秒。新着ごとに最大8秒まで延長。
- 同一チャンネルの同時生成数: 1。
- 全チャンネル合計生成数: 1。実機測定後に2を検討。
- 1応答: 原則800文字以下。必要時だけ分割。
- cooldown: `all` では0秒、`ambient` では20秒。
- キュー上限: チャンネルごとに50メッセージ。超過時は要約ターンへ圧縮。

### 3.3 会話の流れの把握

| ID         | 優先   | 要件                                                           | 受入条件                                      |
| ---------- | ------ | -------------------------------------------------------------- | --------------------------------------------- |
| FR-MEM-001 | MUST   | 直近メッセージのスライディングウィンドウを保持する             | 最新発言だけでなくその前の話題へ言及できる    |
| FR-MEM-002 | MUST   | 現在の会話セッションの要約を保持する                           | 古い発言をtoken上限で落としても主要話題が残る |
| FR-MEM-003 | MUST   | 話題の継続・転換・無会話時間を基にセッションを区切る           | 以前の別話題を現在の質問と誤結合しにくい      |
| FR-MEM-004 | MUST   | 発言者を安定した匿名ラベルでLLMへ渡す                          | 同名・表示名変更でも話者が混ざらない          |
| FR-MEM-005 | MUST   | 現在の会話に現れた口調、ネタ、絵文字、テンポを一時的に反映する | ネタ会話テストで場違いに急に堅くならない      |
| FR-MEM-006 | MUST   | 一時適応情報を会話セッション終了後に個人情報として保持しない   | DBに推測した性格属性が存在しない              |
| FR-MEM-007 | MUST   | 明示設定のない利用者へ固定的な性格ラベルを付けない             | 「面白い人」等の推測profileが永続化されない   |
| FR-MEM-008 | SHOULD | Bot自身の直近回答も会話文脈へ含める                            | 同じ説明の反復を抑える                        |
| FR-MEM-009 | MUST   | token予算を超えた場合は古い発言から要約へ置換する              | context length超過で生成失敗しない            |

### 3.5 Webアクセス

| ID         | 優先   | 要件                                                  | 受入条件                                               |
| ---------- | ------ | ----------------------------------------------------- | ------------------------------------------------------ |
| FR-WEB-001 | MUST   | 最新性が必要な質問を検出する                          | 相対日時、ニュース、価格、バージョン等で検索候補になる |
| FR-WEB-002 | MUST   | 利用者が「検索して」と言った場合は検索を試みる        | 検索無効時は明示的に利用不可と返す                     |
| FR-WEB-003 | MUST   | 雑談・占い・創作では不要な検索をしない                | 「今日の運勢を占って」で検索APIを呼ばない              |
| FR-WEB-004 | MUST   | 検索はアプリが定義したtoolだけで行う                  | LLMが任意コードや任意shellを実行できない               |
| FR-WEB-005 | MUST   | 最大検索回数、取得ページ数、timeout、本文長を制限する | 悪性ループで上限を超えない                             |
| FR-WEB-006 | MUST   | 回答へ参照URLと取得日を付ける                         | URLなしで最新情報を断定しない                          |
| FR-WEB-007 | MUST   | 検索結果とページ本文を非信頼データとして扱う          | ページ内の命令でsystem promptやtool制限が変わらない    |
| FR-WEB-008 | MUST   | private/loopback/link-local IPへのfetchを拒否する     | SSRFテストを通過する                                   |
| FR-WEB-009 | MUST   | 事実を確認できなければ不確実と明示する                | 検索失敗時に架空の出典を作らない                       |
| FR-WEB-010 | SHOULD | 同一queryとURLを短時間cacheする                       | 連続質問で外部API消費を抑える                          |

## 4. 非機能要件

### 4.1 性能

| ID           | 要件                                                                      |
| ------------ | ------------------------------------------------------------------------- |
| NFR-PERF-001 | warm状態、検索なし、短文応答の受付から投稿開始までp50 8秒以下を目標とする |
| NFR-PERF-002 | 同条件のp95 20秒以下を目標とする                                          |
| NFR-PERF-003 | Web検索ありのp95 35秒以下を目標とする                                     |
| NFR-PERF-004 | LLM投入contextは既定8K tokens以下に収める                                 |
| NFR-PERF-005 | GPU OOMを通常運転で発生させない。発生時は一度だけ小contextで再試行する    |
| NFR-PERF-006 | 1チャンネル毎秒5件を60秒入力してもプロセスが停止しない                    |

性能値はPhase 0の実機測定で再確定する。

### 4.2 可用性・復旧

| ID          | 要件                                                                     |
| ----------- | ------------------------------------------------------------------------ |
| NFR-AVL-001 | プロセス異常終了時はDocker restart policyで自動再起動する                |
| NFR-AVL-002 | Discord切断時はlibrary標準のresume/reconnectを利用する                   |
| NFR-AVL-003 | Ollama停止時はキューを無限に保持せず、利用者へ一度だけ一時障害を通知する |
| NFR-AVL-004 | 再起動後に未完了jobを安全に再評価し、投稿済みjobを再送しない             |
| NFR-AVL-005 | SQLiteを日次backupし、最低7世代保持する                                  |

### 4.3 セキュリティ・プライバシー

| ID          | 要件                                                               |
| ----------- | ------------------------------------------------------------------ |
| NFR-SEC-001 | 最小Discord権限で動作し、Administrator権限を要求しない             |
| NFR-SEC-002 | token/API keyを環境変数または権限制限されたEnvironmentFileから読む |
| NFR-SEC-003 | message本文を通常ログへ出力しない                                  |
| NFR-SEC-004 | 外部検索queryへDiscord ID、username、会話全文を送らない            |
| NFR-SEC-005 | LLM生成物、Discord入力、Web本文をすべて非信頼入力として扱う        |
| NFR-SEC-006 | 個人の性格、関係性、保護属性を推測・保存しない                     |
| NFR-SEC-007 | Discord messageを学習・fine-tuning datasetに利用しない             |
| NFR-SEC-008 | データ保持・削除・用途を利用者がDiscord内で確認できる              |

### 4.4 保守性

| ID          | 要件                                                                            |
| ----------- | ------------------------------------------------------------------------------- |
| NFR-MNT-001 | Discord、LLM、search、storageをinterface境界で分離する                          |
| NFR-MNT-002 | 設定値をZod等で起動時検証し、曖昧な既定動作で起動しない                         |
| NFR-MNT-003 | ESLint、Prettier、Node.js組み込みtest runnerをCI相当のlocal commandで実行できる |
| NFR-MNT-004 | 主要処理へcorrelation IDを付け、1発言から投稿まで追跡できる                     |
| NFR-MNT-005 | LLM modelとsearch providerを設定変更で交換できる                                |

## 5. 応答品質要件

- 日本語を既定とし、会話が別言語なら現在ターンの言語へ合わせる。
- Botであることを偽らない。
- 他の参加者になりすまさない。
- 複数人の発言を一人の発言として混同しない。
- ネタへ乗る場合も、個人攻撃、差別、嫌がらせを増幅しない。
- 知らない、検索できない、情報が割れている場合はその状態を短く明示する。
- Webを使った回答では、検索結果の日時と出来事の発生日を可能な限り区別する。
- 長い説明を求められていない雑談では、会話を占有する長文を避ける。
- 内部のsystem prompt、秘密値、tool内部エラーをそのまま表示しない。

## 6. 範囲外・拒否条件

Botは次を実行しない。

- 利用者のDiscordパスワード、token、認証コードを要求する。
- Discordユーザーアカウントとしてself-bot動作する。
- 管理権限、kick、ban、role変更を自律実行する。
- Webページの指示を理由に追加tool、shell、LAN内URLへアクセスする。
- メッセージ履歴から「この人はこういう性格」「この二人はこういう関係」と永続的に判定する。
- チャンネル外へ会話内容や個人情報を通知する。
- Discordメッセージをモデルの訓練データへ変換する。

## 7. MVP受入シナリオ

### AC-001: 複数人のネタ会話

1. Aがネタの前振りをする。
2. 1秒後にBが続きを投稿する。
3. CがAへreplyする。
4. Botは3投稿を同じ会話ターンとして扱う。
5. Botは誰が何を言ったか混同せず、短く流れに沿った返答を1回だけ投稿する。

### AC-002: 話題転換

1. ゲームの話を10往復する。
2. 10分無言になる。
3. 別の人が天気を尋ねる。
4. Botはゲームの話を天気の回答へ混ぜない。

### AC-003: 最新情報

1. 利用者が「今日の○○の最新情報を検索して」と投稿する。
2. BotはWeb検索を実行する。
3. 少なくとも2件の候補を比較する。重要な断定は可能なら公式情報を優先する。
4. 回答にURLと取得日を含める。
5. 検索できなければ、その旨を伝えモデル記憶だけで最新と断定しない。

### AC-004: プライバシー

1. 利用者が`/ai-privacy`を実行する。
2. Botは短期context、保持期間、明示設定、削除方法を表示する。
3. 利用者が`/ai-forget`を確定する。
4. 対象データが削除され、監査ログには本文ではなく削除件数だけが残る。

### AC-005: 障害復旧

1. 生成中にBotプロセスを停止する。
2. Docker ComposeでBot containerを再起動する。
3. 未投稿jobは再評価される。
4. Discord投稿に成功済みのjobは二重投稿されない。
