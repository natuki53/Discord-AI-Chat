# プロジェクト計画書

## 1. プロジェクト概要

Discord の指定チャンネルに AI が一参加者として常駐し、複数人の発言を順番・返信関係・話題単位で把握して自然に返答する Bot を構築する。ローカル LLM によるプライバシーとランニングコストの抑制を優先し、必要な場合だけ Web 検索を使って最新情報を補う。

### 1.1 目標

- 人間同士の会話を遮断せず、直前のネタや話題に沿った返答をする。
- 指定チャンネルに投稿された人間のメッセージを取りこぼさず処理する。
- 複数人の発言順と「誰が誰に返したか」を理解する。
- 「今日」「最新」「現在の価格」「最近のニュース」など、モデルの学習時点だけでは答えられない質問を検索して答える。
- Discord の規約と利用者のプライバシーを守る。
- WebUI なしで、SSH と Discord コマンドから運用できる。
- RTX 2060 6GB で無理なく常時稼働できるモデル・コンテキスト量に調整する。

### 1.2 成功条件

MVP は次の条件をすべて満たしたとき完了とする。

1. allowlist に指定したチャンネル以外では一切応答しない。
2. 対象チャンネルの人間の新規メッセージを 99% 以上取り込み、重複応答しない。
3. 連投時に発言順が崩れず、古い話題への遅延返信を抑制できる。
4. 直近の話題と参加者を含むテスト会話 30 ケース中 24 ケース以上で、評価者が「流れに沿っている」と判定する。
5. 最新情報テストでは検索を実行し、回答に実在する参照 URL と取得日時を示す。
6. Bot 停止・再起動後も処理済みメッセージの再投稿を起こさない。
7. `/ai-privacy`、`/ai-preferences`、`/ai-forget` が仕様どおり動く。
8. Discord トークンや API キーがログ、SQLite、Git のいずれにも残らない。

## 2. スコープ

### 2.1 MVP に含むもの

- Discord Gateway への接続
- 指定 Guild・チャンネルの allowlist
- 新規メッセージ、編集、削除イベントの取り扱い
- チャンネルごとのキューと連投のまとめ処理
- 直近会話と会話セッション要約
- 返信、メンション、話者情報の文脈化
- ローカル LLM による日本語チャット
- LLM のツール呼び出しによる Web 検索と安全なページ取得
- 参照 URL 付き回答
- 本人が設定した会話上の好み
- SQLite 永続化
- JSON 構造化ログ、Docker Compose 常駐、バックアップ
- 管理・プライバシー用スラッシュコマンド

### 2.2 MVP に含まないもの

- 管理用 WebUI
- 過去ログ全体の一括収集、マイニング、ユーザー性格分析
- 個人間の関係性推定
- メッセージを使ったモデルの学習・微調整
- DM の読み取り・自動送信
- 音声チャンネル参加、VOICEVOX 読み上げ
- 画像生成、画像認識、ファイル解析
- 複数サーバーをまたぐ記憶共有
- 複数 Bot インスタンスの水平分散
- 自動モデレーションやユーザー処分

### 2.3 将来候補

- VOICEVOX による読み上げ。ただし GPU 競合と利用規約を別途検証する。
- 画像添付の説明や OCR。
- Bot が反応する頻度を学習ではなく管理者の明示設定で時間帯別に変更する。
- PostgreSQL と外部ジョブキューへの移行。
- 管理者向けの CLI ダッシュボード。

## 3. 前提と制約

### 3.1 ハードウェア

- ホスト名想定: `home-server-2`
- CPU: Ryzen 5 3500
- GPU: NVIDIA RTX 2060 6GB、1枚
- GPU メモリが 6GB のため、MVP は 3B～4B クラスの量子化 instruct モデルから選ぶ。
- 7B～8B クラスはモデル本体だけでなく KV cache と実行オーバーヘッドも必要なため、比較ベンチマークの対象にはするが既定値にはしない。
- 会話用コンテキストはまず 8K tokens を上限とし、Web検索時もページ本文を圧縮して投入する。

### 3.2 ソフトウェア

- Linux の systemd と Docker Compose を利用できる環境を前提とする。
- Node.js 24 をDocker image、`package.json` の `engines`、lockfileで固定する。
- JavaScript ESM を使用する。TypeScript のコンパイル工程は導入せず、JSDoc と実行時スキーマ検証で型の事故を抑える。
- ローカル推論サーバーは実機で稼働中の Ollama を使用する。
- 本番のBotとSearXNGはDocker Compose、Ollamaはhostのsystemd serviceで管理する。

### 3.3 Discord

- Discord Developer Portal で Bot Application を作成し、Bot Token を発行する必要がある。
- `MESSAGE_CONTENT` privileged intent を有効にする必要がある。
- 対象チャンネルに `View Channel`、`Read Message History`、`Send Messages` の権限が必要となる。
- メッセージ取得 API は1回最大100件であるが、MVP は古い履歴の一括取得を行わない。
- Discord イベントは重複・欠落・順不同があり得るものとして冪等に処理する。

## 4. 進行フェーズ

### Phase 0: 環境・性能スパイク

目的は、推論モデルとレスポンス目標を実機で確定すること。

- `nvidia-smi` と Ollama の GPU 利用を確認
- 3B～4B の日本語・ツール呼び出し品質を比較
- 4K / 8K context、短文 / 長文、同時キュー時の速度と VRAM を計測
- LLM モデル、量子化、コンテキスト、生成上限を決定
- 検索プロバイダーを決定

完了条件: `09-decisions-and-open-items.md` の D-008 と D-009 を確定できること。

### Phase 1: Discord 基盤

- Node.js プロジェクト作成
- 設定読み込み、ログ、SQLite migration
- Discord 接続、intent、allowlist
- メッセージ保存、編集、削除、冪等性
- `/ai-status`、`/ai-privacy`
- `shadow` モードで受信のみ確認

完了条件: 24時間の shadow 運転で対象チャンネルの取りこぼし・重複がないこと。

### Phase 2: 基本会話

- チャンネル単位キュー
- debounce による会話ターン化
- 直近コンテキスト作成
- Ollama 接続、typing 表示、Discord 投稿
- `all` / `ambient` / `mention` モード
- stale response の破棄

完了条件: 複数人の連投とチャンネル並行会話の結合テストを通過すること。

### Phase 3: 会話セッションと適応

- 話題境界の判定
- セッション要約の生成・更新
- 現在の発言から一時的な口調・ネタの流れを抽出
- 明示的な `/ai-preferences` と `/ai-forget`
- コンテキスト予算管理

完了条件: 会話品質評価で目標値を満たし、個人の推測情報が永続化されていないこと。

### Phase 4: Webアクセス

- freshness 判定
- 検索・ページ取得ツール
- SSRF、サイズ、時間、Content-Type 制限
- 出典整形、取得日時、検索失敗時のフォールバック
- prompt injection 耐性テスト

完了条件: 時事質問・通常質問・悪性ページのテストを通過すること。

### Phase 5: 運用化

- Docker Compose、volume、secret fileの権限
- ログローテーション、DB バックアップ、復元試験
- watchdog、ヘルスチェック、障害通知
- 72時間の試験運転
- ランブック完成

完了条件: 再起動、ネットワーク断、Ollama停止、検索障害から期待どおり復旧すること。

## 6. 推奨実装順と見積り単位

| 作業                 |     規模目安 | 依存         |
| -------------------- | -----------: | ------------ |
| 性能スパイク         | 0.5～1.5人日 | なし         |
| プロジェクト基盤・DB |     1～2人日 | 性能スパイク |
| Discord 受信・キュー |     1～2人日 | 基盤         |
| 会話生成             |   1.5～3人日 | 受信、Ollama |
| セッション要約・好み |     2～3人日 | 会話生成     |
| Web 検索             |     2～3人日 | 会話生成     |
| セキュリティ・テスト |     2～4人日 | 各機能       |
| 配置・試験運転       |     1～2人日 | 全機能       |

これは実装判断のための相対見積りであり、カレンダー上の納期ではない。モデル品質調整と Discord 上での会話評価は反復回数で変動する。

## 7. リスク管理

| ID    | リスク                                           | 影響 | 対応                                                      |
| ----- | ------------------------------------------------ | ---- | --------------------------------------------------------- |
| R-001 | 6GB VRAM でモデルまたは長い context が収まらない | 高   | 3B～4B Q4、8K上限、Web本文圧縮、実機測定                  |
| R-002 | すべての発言に返信して会話を邪魔する             | 高   | 連投を束ねる、モード切替、cooldown、`/ai-pause`           |
| R-003 | 古い返答が新しい話題へ割り込む                   | 高   | generation version、stale判定、中止・再生成               |
| R-004 | Discord 規約に反する個人プロファイル             | 高   | 履歴分析なし、短期文脈のみ、本人指定の好みのみ保存        |
| R-005 | Web ページの prompt injection                    | 高   | Web本文を非信頼データとして分離、ツール上限、命令無視     |
| R-006 | Web fetch の SSRF                                | 高   | private IP拒否、DNS再検証、redirectごとに検証             |
| R-007 | Bot同士の無限会話                                | 高   | Bot・Webhook・自分の投稿を除外                            |
| R-008 | Discord / 検索 API の rate limit                 | 中   | ライブラリの制御、キャッシュ、指数backoff、キュー上限     |
| R-009 | ローカル LLM が不正確                            | 中   | 検索出典、不確実性表示、回答拒否、品質テスト              |
| R-010 | DB破損・ディスク故障                             | 中   | WAL、定期backup、復元テスト、保持期間制限                 |
| R-011 | Bot token 流出                                   | 高   | EnvironmentFile、ログredaction、Git除外、即時rotation手順 |

## 8. 変更管理

- 要件変更は `02-requirements.md` の要件IDを更新する。
- 仕様上の重要判断は `09-decisions-and-open-items.md` に決定記録を追加する。
- 依存パッケージと LLM モデルは再現可能な名前・digest・設定を記録する。
- プライバシー境界、保持期間、対象チャンネルを広げる変更は通常の機能変更より一段高いレビュー対象とする。
- 本番チャンネル投入前に shadow → limited → full の順に段階公開する。
